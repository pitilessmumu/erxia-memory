# 踩坑全史

这是做这套东西时踩到的坑，一条一条记的，共 78 条。

放出来是因为**你大概率会踩到同样的坑**。这些不是从文档看来的，是真错了、真炸了、真花了时间才搞明白的——所以它比代码有用：代码谁都能写，坑不能。

看的时候注意两件事。

一、这些坑是照着**我们的用法**踩的（一个人加一个 AI，写代码为主）。换了用途，坑的形状会变，但底下那类病是一样的：静默、阈值不缩放、缓存不失效、自己考自己。

二、每条后面都写着「改好了吗」。有些写的是**已修·没验**——代码改了、跑得通，但从没造出那种错来验过。这种真出事的时候不一定叫。我们把它标出来，是因为把「改过」当「修好」正是这套东西最容易犯的错。

每条格式固定：怎么踩的、怎么改的、改好了吗、锁在哪、别再试什么。最后一项是用重复劳动换来的——**别再去试那条路，试过了，不成立**。

# 记忆插件 · 踩坑全史

从 2026-10-30 动手到现在，踩过的每一个坑。

每条写四样：**怎么踩到的、怎么改的、改好了吗、凭什么算改好**。

**「改好了吗」分五档，比上一版细了一层：**

- **已修·验过**：有回归锁着，或者造出那种错来验过防线动不动
- **已修·没验**：代码改了、跑得通，**但从没真出过那个错，等于没验**
- **一半**：改了一部分，或者只是把问题缩小了
- **没修**：知道有这坑，还没找到办法
- **边界**：不是能修的坑，是这套系统的固有边界

第三档和第四档最容易骗人——「改了」和「改对且验证过」是两件事。

**五档在决策时算什么（硬规矩，2026-11-03 外审定）：**

- **已修·验过** 才算防线。但要看「锁在哪」——有回归锁的、当场报错验的、手动核过的，
  可信度不一样，后者只是「那一次对了」。
- **已修·没验** 一律按**没修**对待。排优先级、宣称能力、对外交接时，都不许算进防线。
  **没造出那种错来看防线动不动，等于防线从未开过火。**
- **一半 / 没修 / 边界**：按字面理解，不算防线。

**为什么定这条**：分了两档但不定后果，那一档会变成安慰剂——二十七条躺在那儿像是完成度八成，
实际是零。分类不是目的，分类的后果才是。

## 一、起步期：声音和球（10-30 ~ 11-01）

### LOCAL-001 · 钩子

**怎么踩的**：进程被 NTFS 打了低完整性标签（Low Mandatory Level），中权限窗口不往低权限进程投输入，低级钩子装上就被静默摘掉；不是通道的问题

**怎么改的**：检查解释器所在目录的完整性级别，用 icacls <目录> /setintegritylevel Medium /T /C 递归改成 Medium，重起进程再测

**改好了吗**：已修·验过 —— 改完实测四通道探针全通

**锁在哪**：改完实测四通道探针全通

**别再试**：**把钩子搬出 GUI 进程单独跑**（只解决第一层（Tk 主循环回调超时），低完整性那层还在，搬完照样冻）；**换原始输入通道**（原始输入只稳定给鼠标移动，按键只有低级钩子拿得到）；**怀疑驱动改映射或游戏反作弊拦截**（四通道探针同时能收到，说明键本身没问题）；**让用户双击启动以继承资源管理器权限**（目录本身是低完整性标签，双击继承来的仍是低权限）

## 三、命令行和 SQL 那些硬骨头（11-01 ~ 11-02）

### LOCAL-019 · 命令行里塞 Python 代码

**怎么踩的**：PowerShell 5.1 的 @"..."@ 会插值：$ 被当变量展开、反引号被当转义符吃掉。把带引号、反引号、中文的 Python 代码当字符串塞进命令行，等于让它改一遍再执行；改坏了报出来的 SyntaxError 指向一个我根本没写过的行，所以每次错象都不同、每次都要重新找。

**怎么改的**：代码一律先写文件（write 工具落盘到 .dsh-switchman\run\_xxx.py），再直接跑那个 .py，命令行里只留一句路径。2026-11-02 一天连踩四次，落盘的四次全没咬人。

**改好了吗**：已修·验过 —— 反复犯四次，每次都是当场报错验的

**锁在哪**：反复犯四次，每次都是当场报错验的

**别再试**：**把 @"..."@ 换成 @'...'@ 接着内联——只是少插值一次，反引号和引号还在打架**（试过不成立（详见该条根因））；**看到 SyntaxError 先去改 Python 代码——错根本不在代码里**（试过不成立（详见该条根因））

**怎么踩的**：扫原文抽失败时，只要正文里出现「失败/错误/Error」就收，于是 grep 命中行、markdown 标题、被中断的工具调用全被当成故障。

### LOCAL-078 段头多一个点，十二段全没进库（2026-11-04）

- **症状**：仓库里的示例语料建库，`db-build.py` 打印「语料 0 段、事 0 条」「入库：段 0、事 0、库 0.0 MB」，**退出码 0**，看着像建成功了。之后所有提问都回「没找到」。
- **根因**：我把段头写成 `## [demo1a2b3c-001] 小满 · 2026-10-30 21:14:03`，中间那个「·」是照注入块的显示格式抄的。真格式没有它：`## [04bf1d5b-001] 报错 2026-11-01 07:04:38`。`SEG_RE` 是拿 `\s*` 卡「谁说的」和时间的，多一个 `·` 整行就不匹配，而解析器对不匹配的行是**静默跳过**。

## LOCAL-073

**一句话**：配置找不到根就猜一个默认值，猜错了不喊

**症状**：根目录找错了，十六个模块一起拿着错路径继续跑；建库脚本报成功，检索全空，没有一个模块喊「路径不对」。

**根因**：`config._find_root()` 最后一句是「往上六层没找到含 origin/ 或 lab/ 的目录，就 `return HERE.parent`」——它不报错，它猜一个。猜错了就是整个依赖网一起走错路。这不是引用失败（那种会当场报错），是你说的连锁死亡。

**解法**：删掉猜测，改成抛 `ConfigError`，消息里写清「设 ERXIA_HOME 或把代码放在 origin 上一层」。另加 `config.check()`，建库/注入这些入口第一行就调。

**别再试**：给它留一个「合理的默认值」——默认值就是猜，猜错了没人喊。

**预防**：凡是写「找不到就用兜底」的地方，问一句：兜底错了谁来喊？没人喊的兜底不是兜底，是掩盖。

## LOCAL-074

**一句话**：sqlite 对不存在的路径静默建空库，空库比没有库更坏

**症状**：以为二十二兆的库被写坏了，查了半天，其实是摸错了路径，sqlite 在错的地方建了个空库，建库退出码还是 0。

**根因**：`sqlite3.connect()` 对不存在的文件会安静地创建；`db.connect()` 原来只判「文件在不在」，不看大小；建库脚本只看退出码、不看行数。

**解法**：`db.connect()` 加一道「0 字节直接拒」，`db-build` 建库前调 `config.check()`、建完验段数。三个地方一起焊。

**别再试**：拿「connect 成功了」当「库是对的」。空库比没有库更坏，因为它看着是好的。

**预防**：任何「打开资源」的调用，后面都补一句「它应该长什么样」——文件多大、几行、几个键。这句就是契约。

## LOCAL-075

**一句话**：改了阈值或打分公式，不报错，所有分数一起悄悄漂

**症状**：把某个门槛从 0.30 改成 0.03，或者把 bm25 的 K1 改错，代码照跑、返回类型不变，只是所有查询的分一起漂、命中一起变差，没有任何一处报错。

**根因**：函数签名没变、类型没变，变的只是「含义」。这类改动没有契约，只能靠人记得跑回归。

**解法**：把取值范围写进代码当接口——`hybrid._check_thresholds()` 在 import 时验一遍，越界当场抛；`corpus.bm25` 对 `avgdl <= 0` 直接返回 0，不拿零当除数（那会 ZeroDivisionError，而在调用方看来只是「这一问没分」）。

**别再试**：指望「改完看跑分」发现——跑分本身可能一起漂，分数变了你还以为是对手变了。

**预防**：注释里的「这个数应该落在 X 到 Y」要变成代码里的断言。写在注释里的约束不会生效，写在代码里的会。
